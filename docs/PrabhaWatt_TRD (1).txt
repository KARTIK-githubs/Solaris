TECHNICAL REQUIREMENTS DOCUMENT (TRD)
=====================================

Client: React + TypeScript + Tailwind; server: Python FastAPI; database: SQLite for demo / PostgreSQL pilot; optimiser: OR-Tools CP-SAT or SciPy MILP; calculations: Python Decimal + pandas; reporting: PDF and CSV; optional reviewed OCR/LLM; import first via CSV/manual. Services remain modular within one deployable backend for hackathon.

4. API CONTRACT SKETCH
POST /auth/session; POST /projects; GET /projects/{id}; POST /communities/{id}/participants; POST /consents; POST /bills; POST /projects/{id}/roof; GET /policy-rules?jurisdiction=...; POST /eligibility/evaluate; POST /quotations; POST /scenarios; POST /scenarios/{id}/solve; GET /scenarios/{id}; POST /allocations/validate; POST /approvals; POST /settlements/import; GET /statements/{id}; POST /assets/{id}/generation-import; GET /assets/{id}/performance; POST /tickets; GET /audit?project_id=...
Errors: 400 invalid input, 401 unauthenticated, 403 forbidden, 409 version conflict, 422 regulatory/constraint rejection, 503 external data unavailable. Never conflate 'requires approval' with HTTP success indicating legal approval.

5. FINANCIAL ENGINE
Inputs: matched period kWh, tariff/slab/fixed charges, roof area, quotation, capacity, expected generation, degradation, O&M, financing term, grid settlement assumptions.
Outputs: modelled annual generation, gross/net project cost, cash flows, payback (if meaningful), sensitivity bands, provenance and warning flags.
Use Decimal for INR; explicitly document tariff model, netting, billing periods and rounding. Estimated solar generation != eligible exported energy != official rupee credit.

6. OPTIMISER SPECIFICATION
Binary x_i = participant selected; candidate capacity K; financing option f; contribution a_i; approved shares w_i when variable shares are legally permitted.
Primary objective: maximise sum_i x_i; secondary lexicographic minimise cost or maximise minimum net benefit.
Constraints: selected participants eligible/consented; a_i <= budget_i; funding balance; roof/capacity limits; nonnegative shares; sum shares=1 for active participants; minimum participation; model-specific share constraints; no unsupported cross-meter allocation.
Implementation: pre-validate; create immutable input snapshot; solve with timeout; independently verify all constraints; return objective, status, rejected reasons, source assumptions; never claim 'optimal' without solver proof.

7. ALLOCATION ENGINE
For matched period U=sum(u_i), internal variable-cost share c_i=C*u_i/U where U>0. Ownership-based modelled benefit b_i=B*w_i where approved shares sum to 1. Alternative consumption-weighted/hybrid benefit only internal what-if unless authorised.
Use official settlement data for verified credits; track source document and imported date. Prevent double counting of credits already in net utility bills. Rounding remainder assigned by deterministic documented method; reconcile totals exactly.
State machine: DRAFT_MODEL -> MEMBER_APPROVED_PROPOSAL -> DISCOM_SUBMITTED -> DISCOM_APPROVED -> OFFICIAL_SETTLEMENT_IMPORTED -> RECONCILED; evidence required for transitions.

8. RULE ENGINE / GOVERNANCE
Store immutable policy versions with source, date, geographic scope, consumer category, arrangement, requirements, exceptions and reviewer. Rules default to 'INSUFFICIENT_EVIDENCE' if no matching authoritative source. Human review before policy activation. Flag Sep 2026 Delhi amendment and latest DERC consolidated text as mandatory verification tasks before live pilot.

9. SECURITY AND PRIVACY
RBAC and per-project ownership checks on every endpoint; signed sessions, CSRF protections as applicable, TLS, secure secret management, encrypted backups, redacted logs, rate limits, malware scanning of uploads, file size/type limits, audit access, consent-based disclosures. Tenant isolation tests required. No private household budget in installer views by default.

10. INTEGRATION BOUNDARIES
CSV/manual: bills, quotes, generation, settlement. Optional OCR only after user verification. No real DISCOM billing API, credit transfer, or inverter integration claimed in MVP. Future integrations require contracts, authentication, source validation and reconciliation.

11. TEST STRATEGY
Unit: slab tariffs, unit conversion, finance schedules, rounding, no-double-credit, solver constraints.
Property: sums of shares and rupees, nonnegative values, monotonically constrained affordability where applicable.
Integration: auth/consent, project lifecycle, policy version pinning, settlement import.
Security: cross-tenant access, IDOR, upload validation, role escalation.
Demo: 20-flat synthetic case; 10/12/15 kW; withdrawal and budget sensitivity; MSME scenario; synthetic O&M.

12. OPERATIONS
Development via Docker Compose; separate config for demo/pilot; Alembic migrations; structured logs, health checks, backups, rollback, audit retention and error monitoring. Do not publish real consumer data in sample repos.
