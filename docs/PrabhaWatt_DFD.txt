DATA FLOW DIAGRAMS (DFD) AND DATA DICTIONARY
============================================
NOTATION: [E#] external entity; (P#) process; ||D#|| data store; --> data flow. These are text-based logical DFDs, not physical wiring diagrams.

LEVEL 0: CONTEXT DIAGRAM
[E1 Resident/RWA/MSME] -- bills, budgets, consent, project details --> (P0 PRABHAWATT)
[E2 Installer/Financier] -- quotes, terms --> (P0 PRABHAWATT)
[E3 Technician/Inverter CSV] -- service and generation records --> (P0 PRABHAWATT)
[E4 DISCOM/Authorised documents] -- published rules, approval evidence, official settlement (imported by authorised user) --> (P0 PRABHAWATT)
(P0 PRABHAWATT) -- feasibility, scenarios, proposed allocations, internal statements, alerts --> [E1]
(P0 PRABHAWATT) -- consented enquiries/project scope --> [E2]
(P0 PRABHAWATT) -- work orders --> [E3]
NOTE: No direct power flow, automated utility credit transfer, or official bill issuance.

LEVEL 1: MAIN PROCESSES
[E1] --> (P1 Identity/Consent/Onboarding) --> ||D1 Users/Organisations/Consents||
[E1] --> (P2 Bill and Project Intake) --> ||D2 Bills/Meters/Roofs/Projects||
||D2|| + ||D3 Versioned Policy Rules|| --> (P3 Eligibility Gate) --> ||D4 Eligibility Decisions||
||D2|| + ||D4|| + [E2 quotes] --> (P4 Feasibility/Finance) --> ||D5 Scenario Inputs/Outputs||
||D5|| + ||D1|| + ||D4|| --> (P5 Affordability Optimiser) --> ||D6 Solver Runs/Proposals||
||D6|| + ||D7 Approvals/Settlements|| --> (P6 Allocation/Reconciliation) --> ||D8 Internal Statements||
[E3] --> (P7 O&M Monitor) --> ||D9 Generation/Tickets||
(P3)-(P7) --> (P8 Reports/Audit) --> ||D10 Audit Events/Exports||
(P8) --> [E1 Auditor/Coordinator]

LEVEL 2A: ELIGIBILITY GATE
(P3.1) Determine geography/DISCOM/consumer category/meter model.
(P3.2) Select matching dated policy version from ||D3||.
(P3.3) Check roof rights, metering eligibility, subsidy category and required approvals.
(P3.4) Return ELIGIBLE_AS_MODELLED / REQUIRES_APPROVAL / INELIGIBLE / INSUFFICIENT_EVIDENCE, with cited reasons.
(P3.5) Block unsupported official credit modelling; persist decision in ||D4||.

LEVEL 2B: COLLECTIVE OPTIMISATION
(P5.1) Snapshot member consent, budgets, bills and eligible model.
(P5.2) Enumerate project capacity and financing choices.
(P5.3) Formulate participant selection, funding, roof and legal share constraints.
(P5.4) Solve, then independently validate constraint satisfaction.
(P5.5) Compare baseline equal-share plan and stress scenarios.
(P5.6) Save versioned plan, exclusions, solver proof/status to ||D6||.

LEVEL 2C: CREDIT/FINANCIAL ALLOCATION
(P6.1) Load approved allocation policy and participant weights.
(P6.2) Load modelled export for forecasts OR verified official settlement for reconciliation.
(P6.3) Calculate participant shares and internal charges separately.
(P6.4) Reconcile 100% shares, total INR, matched billing periods, rounding.
(P6.5) Detect existing netted credits and block double deduction.
(P6.6) Generate labelled INTERNAL STATEMENT and audit record; never an official utility bill.

DATA STORES / SENSITIVE FIELDS
D1 user identities, memberships, consent and private budget references [restricted].
D2 utility bills, meter identifiers, consumption, roof rights, project inputs [restricted].
D3 sourced policy rules, effective dates, approved models [admin versioned].
D4 eligibility decision, reason codes, rule version [auditable].
D5 assumptions, quotes, tariff snapshots, scenario outputs [versioned].
D6 solver inputs/outputs, participant proposals, explanations [private project].
D7 consented approvals and imported DISCOM settlement evidence [restricted].
D8 internal cost/benefit statements [participant scoped].
D9 asset telemetry, performance and service tickets [asset scoped].
D10 audit and report metadata [tamper-evident controls].

TRUST BOUNDARIES
TB1 Browser -> API: authenticated and validated requests.
TB2 Participant -> coordinator: aggregate-only views by default; private budget access only with consent and defined role.
TB3 Installer/financier -> project: quote-only scoped access, no household bills.
TB4 External documents -> policy/settlement: verified provenance; imported data not assumed authoritative without review.
TB5 Calculation -> report: immutable snapshot and rule version, labels 'estimated' vs 'verified'.

ERROR FLOWS
Missing consent -> block intake/sharing.
Unknown policy -> insufficient evidence, no credit eligibility claim.
Solver infeasible -> explanation and alternative smaller capacity/financing scenario.
Missing official settlement -> forecast only, no verified credit.
Unmatched periods -> block final statement.
